## Finding

### P2 — a pending native IndexedDB open strands even a valid synchronous checkpoint

**Location:** `src/App.tsx:119` through the restoration/finalization at `src/App.tsx:134`; the validated localStorage checkpoint is only installed after `loadGame(content)` settles. `ready` remains false until that promise settles, and `src/App.tsx:403` returns only the loading screen. `src/save.ts` opens the database without a bounded fallback for a request queued behind another connection operation.

**Concrete native reproduction, without a fake IndexedDB implementation or game-state setter:**

1. In a fresh production Chromium context, open seed 42, open table 1, and let the initial save settle.
2. Open another same-origin page, retain a real `indexedDB.open("junyan-waiter", 1)` connection, and request `indexedDB.deleteDatabase("junyan-waiter")`. Its native `blocked` event confirms the deletion is waiting on that retained connection.
3. In the game page tap 包子 and immediately reload. The synchronous checkpoint contains `journal.bun`, but the new database open queues behind the blocked deletion.
4. The only visible content remains `早安，小馆正在开门。`; no 开门迎客 control becomes available within the independently asserted three-second bound. An ordinary healthy startup completes well within the same bound. The open has neither an error nor a blocked notification of its own to settle the awaited promise.

**Impact:** another tab's pending database operation can indefinitely prevent play and access to already checkpointed progress, even though localStorage is usable. This is an availability failure, not evidence that the checkpoint bytes were lost. A normal denied-storage rejection already recovers correctly. This dependency is inherited from the asynchronous startup design, but the newly introduced recovery checkpoint does not bypass it.

**Evidence:** `output/0044/native-blocked.cjs`, `native-blocked.log`, `native-blocked-results.json`, and `native-blocked-delete-with-valid-checkpoint-failure.png`. The separate synthetic `blocked-open` fault also fails on the worker-only version; distinguish that boundary simulation from the native queue reproduction.

**Missing regression:** a browser test with a retained real second connection, a blocked deletion and a queued game open, asserting bounded playable startup and restored journal content. The proposed save worker's simulated `onblocked` tests do not exercise an open that receives no such event. The writer should decouple usable checkpoint restoration from an unbounded load, or introduce a bounded fallback with cancellation/generation fencing so a late load cannot overwrite subsequent gameplay. Do not add an unguarded late `setState` race.

**Save-worker compatibility result:** the synthetic `blocked-open` scenario changes from FAIL to PASS with `0b79e33`, and all nine independent synthetic/storage scenarios then pass. The native queued-open case still fails. Read-only native event instrumentation records exactly `["open"]` while the loading screen persists; closing the retained connection releases the queue and the game then restores 包子 successfully. This distinguishes an actual unbounded dependency from a merely slow test or corrupt checkpoint. See `native-blocked-events.json`, `native-blocked-before-release.png`, and the combined rerun log.

### P2 — WebKit can restore focus to BODY instead of the initiating customer

**Location:** `src/App.tsx:231` captures `document.activeElement` in the post-render modal effect; `src/App.tsx:235` later focuses that captured node. The background becomes inert in the modal render (`src/App.tsx:406` and `src/App.tsx:437`), so an opener can already have lost focus before it is captured.

**Reproduction:** in native WebKit production, use actual Option-Tab/Enter to open the game and the **1桌 customer-row** control; open 包子 by keyboard, Escape the word card (word-trigger restoration succeeds), then Escape the table. Wait until no dialog remains and assert the initiating customer row is focused. Intermittently `document.activeElement` is BODY instead. A standalone minimal run reproduced this on desktop; the longer real-user route also reproduced it on both desktop and 390px phone. Other attempts passed, so this is an intermittent failure, not a universal inability to Tab in WebKit.

**Impact/evidence:** closing the dialog loses the player's keyboard place; subsequent tabbing restarts elsewhere instead of resuming from the opener. `output/0044/focus-return.cjs`, `combined-focus-return-results.json`, and `combined-webkit-desktop-focus-return-focus.json` record the minimal route. The instrumentation wraps native `HTMLElement.focus` only to log and forward its original call; it records the cleanup calling **BODY.focus()**, with a connected, non-inert BODY, rather than the initiating button. There is no game-state or DOM-focus setter in the driver. Chromium passes both minimal viewport cases. The longer attempts and their failures are retained in `combined-first-results.json`, `combined-first-webkit-keyboard-results.json`, and `combined-first-webkit-phone-focus.json`.

**Missing regression/remediation:** native-WebKit modal closure coverage that asserts the actual original opener, including nested word Escape and kitchen closure, without replacing focus with `locator.focus()`. Capture the explicit opener before making its containing region inert; preserve that opener through a walk. This is the existing post-render restoration design, not a new save-module API incompatibility; the worker's successful Chromium tests do not prove it across engines.

**Historical control:** the same minimal real-keyboard runner against a separately built `git archive 5dfad15` production control reproduces the desktop WebKit failure (and both Chromium cases pass). The phone control passed this particular attempt, consistent with intermittency. Therefore this is an inherited defect exposed by broader review, not a demonstrated regression caused by either applied worker. Results: `baseline-focus-return-results.json` and `baseline-focus-return.log`.

## What the App audit establishes

- `src/App.tsx:74`: dispatch reduces from `stateRef.current`, synchronously checkpoints a substantive result before publishing it to React, then updates both ref and state. Multiple actions in one turn consume the preceding action's state, rather than a captured render snapshot. Movement does not write localStorage every frame.
- `src/App.tsx:112`: recovery JSON is schema/semantic validated, then takes precedence over the IndexedDB snapshot. Invalid JSON/schema falls back to the stored game; thrown storage access surfaces the existing warning. Effect cancellation prevents a superseded StrictMode load from restoring state or enabling an old mount. The ready gate prevents normal gameplay during an ordinary delayed load.
- `src/App.tsx:140`: debounce cleanup cancels scheduled writes, not writes already in flight. The completion compares the exact serialized snapshot before deleting a checkpoint, so an older successful completion cannot erase a newer substantive result. Independent fault injection delayed the first successful completion, aborted the next write, then reloaded: the visible journal retained **听过 2 次**. This is storage-boundary scheduling, not a state hook.
- `src/App.tsx:79`: on checkpoint-write failure, obsolete recovery bytes are removed where permitted and a warning is shown. A quota-path run with two actual word taps, eventual successful IndexedDB persistence and reload retains two lookups instead of restoring the obsolete first checkpoint. If both stores are unavailable, gameplay remains usable and warns, but immediate durability is not promised.
- The keyboard guard excludes startup/day-summary/modals, prevented events and Control/Alt/Meta shortcuts. Escape clears both route and arrival callback. Customer-phase changes rerun the existing focus containment effect, recovering focus after payment removes its trigger without moving an already-contained focus unnecessarily.
